# Olea 0.1.0 terminal WebView fix

## Failure and change

**OBSERVED**: `.setup/release-010/terminal-screen.png` shows a running PTY session with Android WebView's `data:text/html;charset=utf-8;base64,...` error page and `ERR_HTTP_RESPONSE_CODE_FAILURE`. The previous client intercepted only xterm JS/CSS and returned 404 for every other request, while loading the main document with `loadDataWithBaseURL`. The screenshot establishes failure of the display, not failure to create the shell.

**OBSERVED**: `TerminalUi.kt` now loads `https://olea.invalid/terminal.html` with `loadUrl`. The production factory serves exactly three APK resources: the main-frame GET document, subresource GET xterm JS, and subresource GET xterm CSS. Every other intercepted request returns 403; the client never returns `null` for network fallback. Navigation allows only the exact main-frame GET document. File/content access and network loads remain disabled; mixed content is explicitly forbidden.

**OBSERVED**: Response headers restrict scripts/styles to the same origin and the existing inline bootstrap/style, deny other resource types and connections through `default-src 'none'`, and forbid base changes, forms, and embedding. PTY output still enters `terminal.write` through `JSONObject.quote`; output never becomes HTML or executable JavaScript. No terminal assets, backend, runtime, production manifest, or shared UI sources changed.

**OBSERVED**: Required document/asset errors include URL, description, and Android error code. HTTP errors include status/reason; JavaScript console errors from the bundled document/assets include source, line, and bounded message. Rejection of optional resources such as browser-requested favicons does not disable xterm. The Compose viewport displays the first failure and disables its key bar; a ten-second readiness deadline also surfaces silent initialization failures. Leaving and reopening the terminal recreates its WebView without closing the shell.

**OBSERVED**: JavaScript bridge callbacks now post onto the WebView's UI thread. Ctrl conversion and terminal ID are captured before dispatching asynchronous runtime work. Previously the operation closure could observe Ctrl after it had already been cleared. Escape, Tab, arrows, and output use shared script-generation functions so diagnostics exercise the same quoting as production.

## WebView contract review

**OBSERVED**: Android's [WebViewClient reference](https://developer.android.com/reference/android/webkit/WebViewClient) documents that app-initiated `loadUrl` does not call `shouldOverrideUrlLoading`, and that resource interception runs off the UI thread. Thus the fix explicitly serves the main document in the interceptor instead of depending on navigation callbacks; the interceptor uses only immutable resource IDs and resource streams.

**OBSERVED**: Chromium's [`InterceptedRequest::Restart` and `InterceptResponseReceived`](https://github.com/chromium/chromium/blob/main/android_webview/browser/network_service/aw_proxying_url_loader_factory.cc) check `ShouldBlockURL`, then call Java interception, then consume a non-null custom response as an Android stream; only absent interception falls back to the network loader. [`ShouldBlockURL` and `UpdateLoadFlags`](https://github.com/chromium/chromium/blob/main/android_webview/browser/network_service/net_helpers.cc) implement file/content restrictions and network-load cache flags; the network-load pre-interception URL rejection specifically covers FTP, not HTTPS. This source review supports retaining `blockNetworkLoads = true` with a synthetic HTTPS document. It does not establish the connected phone's exact installed WebView implementation.

## Checks and remaining acceptance

**OBSERVED**: `node .setup/release-010/ui-terminal-check.mjs` passes raw input, Ctrl-C, arrows, resize, ANSI/text forwarding, malicious HTML as data, and bundled xterm syntax. `git diff --check` passes for the changed production source. These host checks alone do not prove Android rendering.

**OBSERVED**: Added a terminal-only Android diagnostic, `TerminalWebViewInstrumentation`, and an opt-in Gradle initialization script, `android/terminal-webview-diagnostic.init.gradle`. It uses the production WebView factory and real bundled xterm, without Linux startup, PTY commands, or provider requests. It checks real document URL/readiness, JS/CSS application, xterm resize, exact resource allowlist and blocked navigation, CSP WebSocket/frame rejection, control keys/Unicode/quotes, oversized bridge input, real xterm buffer output, inert malicious HTML, and load/HTTP/JavaScript error callbacks.

**OBSERVED**: The coordinator granted an exclusive host Gradle slot. `:app:compileDebugKotlin` and `:app:compileDebugAndroidTestKotlin` both pass with `-PoleaAbi=arm64-v8a --no-daemon --max-workers=2`. The first attempt compiled production but failed the new diagnostic because Android's `WebResourceError` constructor is not public; the diagnostic now triggers an actual blocked file load instead. The corrected build succeeds, including a final compile after restricting failures to required resources. Local logs preserve the failed constructor attempt and successful results in `.setup/release-010/terminal-compile.log`, `.setup/release-010/terminal-compile-retry.log`, and `.setup/release-010/terminal-compile-final.log`.

**OBSERVED**: A new test manifest alone did not register the diagnostic: AGP rewrote its instrumentation name to the configured `CoreInstrumentation`. That unused new manifest was removed. The opt-in initialization script sets the runner through Android's DSL finalization callback, and the resulting merged test manifest was inspected: package `dev.olea.test`, target `dev.olea`, runner `dev.olea.app.TerminalWebViewInstrumentation`. Compilation with this script also passes (`.setup/release-010/terminal-compile-runner-retry.log`). The first script invocation used an incorrectly doubled `android/` relative path and failed before compilation; `.setup/release-010/terminal-compile-runner.log` retains that invocation failure.

**OPEN**: Android execution of the diagnostic is pending coordinator acceptance. No worker device or provider calls were made. Physical acceptance remains with the coordinator after rebuilding the signed APK: open an existing running terminal, confirm the real prompt/output, type `printf 'terminal-ok\\n'`, test Ctrl-C/arrows and resize, leave/reopen without losing output, and verify a terminal in a second workspace.

**AGENT PLAN**: Build the production and Android-test APKs in the coordinator-controlled slot. Add `-I terminal-webview-diagnostic.init.gradle` when building the terminal diagnostic test APK with `-p android`; normal builds retain `CoreInstrumentation`. For example, with the coordinator's existing Java/SDK/Gradle environment:

```sh
.setup/core/gradle-9.1.0/bin/gradle -p android --no-daemon -PoleaAbi=arm64-v8a -I terminal-webview-diagnostic.init.gradle :app:assembleDebug :app:assembleDebugAndroidTest --max-workers=2
```

With a test APK matching the installed target's signing certificate, run the registered diagnostic using the coordinator's explicitly selected phone:

```sh
adb -s <selected-phone> shell am instrument -w dev.olea.test/dev.olea.app.TerminalWebViewInstrumentation
```

**OPEN**: The diagnostic checks production error callbacks; visual native-error notice and the ten-second fallback require UI acceptance. It does not validate OEM keyboard behavior, PTY transport, session persistence, or signed-APK acceptance. Those are release-manager checks against the actual rebuilt app.
