# Project board: canvas controls and Orca access

## Full-screen canvas and inline cards

**USER DECISION**: Use Excalidraw as the experience reference, with visible creation tools, flexible shapes, creation directly at the pointer, and the whole viewport devoted to the canvas. Sketch styling is not required. The user rejected unfinished-looking cards, prominent blue link arrows, and a separate note editor: notes must be edited inside the note. Source: the user's successive canvas-design corrections in this session. These replace the earlier form-based creation/editing layouts below.

**OBSERVED**: The standalone utility now uses Excalidraw 0.18.1 with React/Vite in `board/`. Its native palette supplies selection, hand, shapes, connectors, drawing, text, images and more tools, plus normal undo/redo and object manipulation. The initial style uses straight strokes and a sans-serif face. Page headers and footers were removed; controls float over the viewport. Custom Note/Task presets preview at pointer scale and place immediately. The native wheel handler is replaced only over the drawing surface to keep pointer-centered wheel zoom.

**OBSERVED**: Note/task cards are grouped canvas primitives with a consistent inset, title/body hierarchy, restrained status pills, optional issue numbers, and shortened previews. Full card content and source URLs stay in metadata. Double-click/Enter edits the selected card at its canvas position through an inline title/content overlay; new notes focus their content. Fields update the drawing as typed. There is no separate note form or properties pane. Native link properties were removed from card drawing primitives so they do not generate blue link badges; references remain available as small text links inside the note. Older saved card links remain in card metadata, with an additional original-scene backup when upgrading the drawing.

**OBSERVED**: Added local scene/library persistence, a Windows launcher, native drawing-file/image actions, and legacy JSON import. `index.html` remains a local-file migration launcher so its former browser storage can be carried to the loopback app without deleting the source. The local utility now requires a Node-hosted page; generated assets/dependencies remain ignored. [User setup](../../board/README.md).

**OBSERVED**: Production build passed. A brief browser/visual pass confirmed a 1440×1000 canvas exactly covering that viewport, immediate note placement, editing within the placed note, persistence after reload, no separate editor, zero native link markers on card elements, and no browser exceptions. A native rectangle was drawn during the earlier spot-check. An early layout assertion incorrectly rejected Excalidraw's floating semantic footer; direct canvas bounds confirmed that it reserves no page space. The earlier card/side-editor previews were rejected by the user and replaced; they are not acceptance evidence for the final design. A narrow-screen view exposed tool crowding; mobile preset controls were moved out of the tool row. No broad native-engine interaction suite, provider tests, or human design acceptance is claimed. Task-lifetime diagnostics were removed after the bounded pass; the local preview remains available on port 4173.

**AGENT PLAN — DESIGN REFERENCES**: Follow visible objects and immediate feedback from NN/g's [Direct Manipulation](https://www.nngroup.com/articles/direct-manipulation/) and keep secondary actions quiet under [Aesthetic and Minimalist Design](https://www.nngroup.com/articles/aesthetic-minimalist-design/). Excalidraw's [source](https://github.com/excalidraw/excalidraw/tree/v0.18.1/packages/excalidraw) and [element conversion API](https://github.com/excalidraw/excalidraw/blob/v0.18.1/dev-docs/docs/%40excalidraw/excalidraw/api/excalidraw-element-skeleton.mdx) ground the tool behavior and native object model. These references guide implementation, not user acceptance or Olea Android product scope.

**OPEN**: User visual review, broad import/export/image recovery, and Orca session integration. Orca access remains feasible as described below, but this canvas change does not connect or send input to sessions.

## General canvas selection and cards

**USER DECISION**: The board is a general canvas; project to-do cards are one form of content. Left-drag on empty space should select cards rather than pan the board, and selected cards should be movable. Source: the user's follow-up canvas-selection clarification in this session. This supersedes the earlier empty-space panning behavior below.

**OBSERVED**: Left-drag now draws a selection box in either direction; intersecting cards are selected. Shift/Ctrl/Cmd click toggles cards, and modified marquee selection adds cards. Dragging a selected card moves the entire selection. A single click selects, double-click or Enter edits, and middle-drag/Space-drag pans. Wheel zoom remains anchored under the pointer. Escape cancels a drag and restores positions, or clears selection. Ctrl/Cmd+A selects visible cards; Delete/Backspace and toolbar Delete ask before deleting. Toolbar Edit supports a single selected card. Filtering prunes selection to visible cards. Focus survives rerendering.

**OBSERVED**: New cards default to plain notes without task-status chrome. The editor can convert notes into tasks and back. Existing saved cards without a `kind` remain tasks; existing positions and content load unchanged. Exports include the optional card kind. Project-document and Orca synchronization remain unimplemented.

**OBSERVED**: Focused headless Chrome checks passed legacy data loading, note/task rendering, single/modifier click, deselection, live/reversed/additive marquee, no panning during marquee, group movement and reload, filtering/select-all-visible, double-click/Enter editing, blank-double-click note placement, note creation/type conversion, mixed note/task export-import roundtrip, cancelled/confirmed multi-delete, keyboard group movement, pointer-anchored wheel zoom, marquee/group movement at non-unit zoom, middle/Space panning, and viewport/editor fit at 1440/768/390 px with no browser exceptions. An initial test exposed lost keyboard focus after Escape rolled back a drag; focus restoration was added and the full focused check rerun passed. Screenshots of note/task layouts and live selection were visually reviewed. Temporary checks used an isolated browser profile and fixture cards, not the user's board storage. Physical mouse/trackpad behavior remains unchecked.

## Earlier canvas controls (superseded selection behavior)

**USER DECISION**: Wheel up/down enlarges/shrinks the board; middle-drag pans; dragging anywhere on a card moves it; clicking without dragging opens editing. Source: the user's canvas-input instruction in this session. The user also asked the agent to infer related interaction improvements.

**OBSERVED**: Implemented in `board/board.js`, `board/board.css`, and `board/index.html`. Wheel zoom anchors at the pointer, including over notes. A five-screen-pixel movement threshold separates clicking from dragging. Card text does not select during dragging, and dragged cards appear above peers. Middle-drag and Space + drag pan over cards; empty-space left-drag still pans. Reference links are accessed from the editor so the whole card shares the same gesture behavior. Enter opens a focused card; existing arrow-key movement remains available. Browser storage format is unchanged.

**OBSERVED**: Task-lifetime headless Chrome checks on a direct file URL passed real pointer dragging/clicking over the header, title, notes, and reference area; small click jitter; middle-drag and Space-drag over cards; empty-space panning; pointer-anchored wheel zoom in both directions; zoom-correct task movement; position persistence through reload; keyboard editing and movement; editor save; reference URL; and pointer cancellation. Screenshots were reviewed at 1440/768/390 px with no page overflow or browser exceptions. Two initial diagnostic assertions needed fixture corrections: CDP wheel coordinates were rounded to integers, and the zoomed-drag fixture was kept inside the viewport. Neither was treated as a product failure. Temporary diagnostic files were removed after use. Physical mouse/trackpad hardware was not tested.

## Orca session access

**OBSERVED**: The installed Orca CLI's version-matched guide documents host-local agent-session search and bounded terminal reads. Session-history indexing was enabled and current at inspection. A conversation-only search scoped to this project returned the board-creation session and the #11/#14 discussion sessions, with titles, timestamps, snippets, structured-session/workspace identifiers, and present transcript source paths. No agent input was sent.

**OBSERVED**: The local Pi transcript returned for the #11 discussion was readable JSONL with user, assistant, and tool-result messages. Only envelope/type counts were printed during inspection. This establishes a practical route to a full Pi chat reader. The current-workspace terminal-list call returned no terminals; that result does not establish that structured chats are absent.

**AGENT PLAN**: For a future board integration, serve the board through a small loopback-only local helper in `board/`. The helper can search Orca for project-scoped sessions and read supported transcript formats on demand. The board can show session cards and open a conversation reader, with task links to particular sessions. Keep transcript data out of committed assets and board exports. The helper is needed because a directly opened web page cannot execute Orca commands or freely read local transcripts.

**OPEN**: No integration was implemented in this change. Full transcript rendering was checked only for the existing Pi format; other agents need their own verified readers. Automatic refresh, in-Orca navigation, remote-host sessions, and a native Orca plugin remain unverified. The initial request here is chat review, so sending prompts is not needed to establish the proposed reader.
