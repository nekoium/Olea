## Findings

1. **RuntimeProbe can abandon a live owned process after an exception.** In `spike/android/app/src/main/java/dev/olea/spike/RuntimeProbe.kt`, after `OwnedProcess.launch` returns, reading the deadline file or waiting/draining can throw (for example `IOException` from the deadline file or `InterruptedException` from `waitFor`/`join`). The catch only records `error`; the finally unconditionally clears `owned` and `running`. Neither path invokes `supervisor.stop()`. The script can continue, and a subsequent STOP finds no owner. Retain the per-launch owner outside the try and perform bounded cleanup on every exceptional exit before clearing the current launch; preserve an explicit unverified cleanup result if cleanup fails. The five checks do not exercise a post-launch failure. This does not invalidate the fixed normal-path gate ordering, but prevents a general failure-cleanup clearance.

2. **The startup-suppression test can race the following teardown test.** `SupervisionInstrumentation.kt` waits for `$attempt.json` and reads it in `probe-stop-before-owned-assignment`, then immediately starts `probe-service-teardown-during-startup`. `RuntimeProbe` creates/writes that file before its finally acquires the monitor and sets `running=false`. The next test can submit its probe while `running` remains true; `run()` silently ignores it. The teardown test then times out at `PROBE_NOT_STARTED` despite correct teardown behavior. File existence can also precede completion of `writeText`, producing a partial-JSON parse failure. Use bounded receipt-completion plus actual launch-idle synchronization, or make receipt publication atomic after state settlement under the same launch monitor. A receipt path alone is not a completion barrier.

3. **Instrumentation failure paths do not isolate subsequent cases.** The immediate-stop and teardown checks lack a cleanup finally; an assertion or wait failure can leave the30s process/service/probe active while the outer loop catches the exception and continues. The next `run` then silently refuses because global `running` remains true. The atomic test does use a finally, but its direct `RuntimeProbe.publish` call never runs the production finalizer, leaving `owned`, `cancelRequested` and `cleanupStarted` populated until a later `run` resets them. Sorting the atomic check first handles only a fresh, successful run; it does not restore fixture state after a failure or an existing cancellation latch. Add bounded per-case settlement and assert clean global launch state, or stop the suite after unsettled cleanup. Independent PID absence remains necessary before interpreting later case failures.
